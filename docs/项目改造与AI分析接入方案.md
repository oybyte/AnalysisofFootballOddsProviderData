# 足球盘口学习与比赛分析项目改造方案

> 文档状态：历史设计记录，保留最初的目标、取舍和数据原则。它不再是当前命令、目录或脚本的操作手册；其中的 `requirements.txt`、`scripts/*.py`、阶段性待办和推荐目录均可能已被实现替代。实际使用请以项目根 `README.md` 和《历史资料提炼、实战场景与规则演进工作流》为准。

## 1. 文档目的

本方案用于将当前项目从一次性的豆包对话整理工程，改造成一个可以长期维护的足球盘口学习与比赛分析资料库。

改造后的项目需要同时满足以下目标：

1. 保留并整理当前学习资料，形成可持续修订的知识库。
2. 每场比赛使用一个独立 Markdown 文件记录完整分析过程。
3. 明确区分赛前事实、赛前推演、临场修正、最终结论和赛后复盘。
4. 支持自动生成比赛索引、复盘统计和阶段性报告。
5. 为后续接入 AI 检索、辅助分析和赛后复盘预留稳定的数据结构。
6. 防止赛后修改赛前判断，以及 AI 回测时发生赛果信息泄漏。

本项目只用于赛事数据学习和分析方法研究，不构成投注建议。

## 2. 当前项目现状

当前目录主要包含：

- 两份约 38 万字节的 Markdown 学习资料。
- 一份包含本地图片的单文件 HTML。
- 251 个图片文件，其中部分文件下载失败或不是有效图片。
- 用于抓取豆包对话、下载图片、清洗文本和生成文档的 Python 脚本。

当前脚本和资料存在以下限制：

1. 数据源、分享 ID、输出文件名和本地路径均有硬编码。
2. 所有比赛、教学内容和复盘内容集中在一个超长对话文档中。
3. 赛前判断和赛后解释没有机器可识别的边界。
4. 缺少统一的比赛编号、球队名称、联赛名称和统计口径。
5. 缺少项目说明、依赖定义、数据格式校验和版本管理规范。
6. 当前文档混合了客观规则、经验判断、具体案例和 AI 生成观点，可信度层级不清晰。

## 3. 总体设计原则

### 3.1 一场比赛一个人工维护文件

每场比赛只维护一个 Markdown 文件。盘口截图、原始网页和结构化缓存属于辅助资料，不作为第二份人工分析记录。

### 3.2 事实、解释和结论分离

- 事实：盘口、水位、欧赔、伤停、时间等可核对信息。
- 解释：对事实可能含义的分析。
- 结论：最终采用的主线、支线和风险判断。

不得把推测写成事实，也不得在赛后用结果倒推并覆盖赛前判断。

### 3.3 赛前记录可追溯

赛前最终结论进入锁定状态后不得覆盖。后续盘口变化只能追加新的临场记录，并说明是否改变原结论。

### 3.4 人工资料是唯一事实来源

Markdown 文件是人工维护的主记录。JSON、索引、统计报告和 AI 检索索引均由脚本自动生成，可以随时重建。

### 3.5 AI 只提供辅助分析

AI 输出必须区分事实、假设、支持证据和反向证据，明确资料缺口和置信度，不得把经验模型描述成确定规律。

## 5. 命名规范

### 5.1 比赛文件名

格式：

```text
YYYY-MM-DD_联赛_主队_vs_客队.md
```

示例：

```text
2026-07-30_韩K联_FC首尔_vs_蔚山HD.md
```

文件名用于人工浏览，不作为程序唯一标识。

### 5.2 比赛唯一标识

格式：

```text
YYYYMMDD-competition-home-away
```

示例：

```text
20260730-kleague-seoul-ulsan
```

`match_id` 创建后原则上不修改。球队改名或出现不同译名时，通过别名表处理。

### 5.3 时间规范

所有时间使用 ISO 8601，并明确时区：

```text
2026-07-30T18:30:00+08:00
```

不得只记录“今晚”“临场前”或“赛前两小时”而缺少绝对时间。

## 6. 比赛生命周期

比赛状态固定为：

```text
draft -> tracking -> locked -> finished -> reviewed
```

- `draft`：刚创建，信息尚不完整。
- `tracking`：正在收集盘口和基本面资料。
- `locked`：赛前最终结论已锁定。
- `finished`：比赛结束，赛果已记录。
- `reviewed`：赛后复盘完成并分类错误原因。

状态不得倒退。特殊情况下需要修正时，必须保留变更记录。

## 9. 盘口记录规范

### 9.1 所有数据必须带时间

盘口变化依赖时间顺序。没有采集时间的数据只能作为静态参考，不能用于判断升盘、降盘或临场动作。

### 9.2 区分盘口事实和方向解释

正确写法：

```text
事实：主让 0.75 从 0.88 升至 0.98，盘口保持不变。
解释：可能表示上盘承压或机构降低上盘吸引力，需要结合欧赔和基本面确认。
```

不建议写法：

```text
主队升水，所以主队一定无法打出。
```

### 9.3 不完整数据必须显式标记

无法获得初盘、机构更新时间或伤停资料时，应写入“缺失信息”，不得由 AI 或人工自行补全。

## 10. 赛前锁定与防止事后修改

### 10.1 锁定规则

执行锁定时：

1. 将状态改为 `locked`。
2. 写入 `locked_at` 和 `data_cutoff_at`。
3. 校验“赛前最终结论”必填字段。
4. 计算赛前锁定区内容哈希。
5. 将哈希写入自动生成的数据文件。
6. 提交 Git 版本。

### 10.2 锁定后的允许操作

- 可以追加临场更新。
- 可以记录赛果和赛后复盘。
- 不得覆盖原始赛前最终结论。
- 发现赛前录入错误时，应追加更正说明，不静默修改。

### 10.3 Git 版本管理

建议初始化 Git，并按以下节点提交：

```text
创建比赛
赛前结论锁定
临场判断更新
赛果录入
赛后复盘完成
```

Git 历史是防止事后改写和追踪分析习惯变化的主要依据。

## 11. 知识库分层

现有资料不能直接全部视为同等可信。知识文档需要使用统一元数据：

```yaml
---
schema_version: 1
document_id: heuristic-handicap-up-water-down
document_type: heuristic
title: 升盘降水的常见解释
reliability: experimental
evidence_level: low
sample_size: 0
scope:
  competitions: []
  handicap_types: []
tags:
  - 升盘
  - 降水
last_reviewed: 2026-07-29
supersedes: null
---
```

### 11.1 文档类型

- `concept`：术语、结算方式等客观知识。
- `method`：标准分析和复盘流程。
- `heuristic`：阻盘、诱盘等经验判断。
- `checklist`：操作检查清单。
- `source`：未经完整验证的原始资料。

### 11.2 可信度等级

- `established`：明确、稳定的客观规则。
- `supported`：有一定样本支持，适用条件相对清晰。
- `experimental`：等待更多案例验证的经验。
- `deprecated`：已经发现明显问题，不应继续作为分析依据。

### 11.3 经验规则必须包含的内容

每条经验规则至少记录：

1. 规则描述。
2. 适用前提。
3. 不适用场景。
4. 支持案例。
5. 反例。
6. 当前样本量。
7. 最后复核时间。

不得因少量命中案例直接将经验规则升级为稳定规律。

## 14. AI 检索和分析设计

### 14.1 不直接加载全部资料

资料增长后，不应将整个目录一次性发送给 AI。正确流程是先建立索引，再按当前任务检索相关内容。

检索优先级建议为：

1. 客观概念和结算规则。
2. 标准分析检查清单。
3. 当前联赛和相似盘口的已复盘案例。
4. 有明确适用条件的经验规则。
5. 原始学习资料。

### 14.2 分块和元数据

索引程序按照 Markdown 章节标记切分内容，并为每个片段附加：

```text
document_id
document_type
match_id
section_type
competition_code
home_team_id
away_team_id
created_at
effective_at
reliability
tags
```

`section_type` 用于区分：

```text
prematch_facts
prematch_reasoning
prematch_locked
live_update
result
postmatch_review
knowledge
```

### 14.3 AI 标准分析流程

AI 分析新比赛时必须按以下顺序执行：

1. 读取当前比赛的客观数据和数据截止时间。
2. 识别缺失信息，不自行虚构。
3. 检索相关概念和分析清单。
4. 检索同联赛、相似盘口和相似变盘的已复盘案例。
5. 对比相似案例中的共同点和不同点。
6. 分别列出支持证据和反向证据。
7. 给出主线、支线、放弃条件和置信度。
8. 明确引用使用过的本地知识和比赛案例。
9. 输出到“赛前推演”或“临场更新”，不得直接修改已锁定内容。

### 14.4 AI 输出契约

每次核心分析至少包含：

```text
已知事实
缺失信息
理论盘口判断
盘口时序判断
支持主线的证据
反向证据
相似案例及差异
主线方向
次选方向
放弃分析条件
置信度及依据
引用资料
```

没有足够信息时，允许并鼓励输出 `pass`。

## 15. 防止 AI 结果泄漏

### 15.1 新比赛分析

分析未来比赛时，可以使用过去已经完成并复盘的比赛，但不得读取当前比赛的赛果和赛后章节。

### 15.2 历史回测

回测某场历史比赛时，只允许使用该场 `data_cutoff_at` 之前已经存在的资料：

```text
retrieved_document.effective_at <= target_match.data_cutoff_at
```

必须排除当前比赛的：

- `result`
- `postmatch_review`
- 赛后更新的知识规则
- 包含最终比分的图片和原始文件

### 15.3 评估报告

所有 AI 回测报告必须声明：

- 数据截止时间。
- 使用的资料版本。
- 是否启用严格时间过滤。
- 是否存在无法排除的潜在泄漏。

没有严格时间过滤的回测结果不得用于评价模型准确率。

## 16. 防止 AI 自我强化

当前资料中包含较多 AI 整理和经验性观点。如果 AI 引用旧 AI 分析，再把新 AI 结论写回知识库，容易形成没有外部证据的循环强化。

控制措施：

1. AI 生成内容必须标记来源和生成时间。
2. AI 结论默认不能直接升级为知识规则。
3. 只有经过人工审核和多个独立案例验证后，才能提高规则可信度。
4. 复盘必须记录反例，不能只保留命中案例。
5. 区分“规则预测正确”和“结果偶然符合”。
6. 样本量较小时不输出强统计结论。

## 17. 统计口径

### 17.1 分层统计

长期统计至少包括：

- 胜平负主线准确率。
- 上下盘方向准确率。
- 大小球区间覆盖率。
- 比分区间覆盖率。
- 不同置信度区间下的准确率。
- 不同联赛、盘口深度和盘路类型的表现。
- 临场改判次数及改判后的净改善程度。
- 主动 `pass` 的比例。

### 17.2 不使用单一总准确率

胜平负、让球方向、总进球和比分区间属于不同难度的任务，应分别评价，不合并成一个笼统的“命中率”。

### 17.3 置信度校准

建议按区间统计：

```text
0.50-0.59
0.60-0.69
0.70-0.79
0.80-0.89
0.90-1.00
```

如果高置信度比赛没有明显高于低置信度比赛的准确率，说明分析体系存在过度自信或置信度定义不稳定。

## 18. 脚本职责

### 18.1 `new_match.py`

- 接收比赛日期、联赛、主客队和开赛时间。
- 生成 `match_id`。
- 创建比赛 Markdown。
- 创建对应图片和原始资料目录。
- 校验是否已存在重复比赛。

### 18.2 `validate_matches.py`

- 校验 YAML 字段和枚举值。
- 校验时间格式和状态流转。
- 检查比赛 ID 是否重复。
- 检查图片引用是否有效。
- 检查已锁定比赛是否缺少最终结论。
- 检查已复盘比赛是否缺少赛果和评价。

### 18.3 `lock_match.py`

- 校验赛前必填项。
- 写入锁定时间和数据截止时间。
- 计算赛前锁定区哈希。
- 将状态更新为 `locked`。
- 提示进行 Git 提交。

### 18.4 `export_match_data.py`

- 从 Markdown 提取标准化 JSON。
- 提取盘口时间序列。
- 提取赛前结论和复盘评价。

### 18.5 `build_index.py`

- 生成按日期、联赛、球队、标签和状态分类的比赛索引。
- 生成 AI 检索片段和元数据。

### 18.6 `build_stats.py`

- 根据已复盘比赛生成统计报告。
- 默认排除未锁定、未结束或未完成复盘的比赛。
- 样本不足时明确提示，不计算误导性百分比。

## 20. 实施阶段

### 第一阶段：建立可维护基础

目标：可以规范地创建和维护新比赛。

- 建立目录结构。
- 初始化 Git。

### 第二阶段：锁定、索引和统计

目标：保证赛前记录可信并可以自动汇总。

- 实现 `lock_match.py`。
- 实现结构化 JSON 导出。
- 生成比赛索引。
- 积累至少 10 场新格式比赛记录。

- 建立严格时间切片回测。
- 检查结果泄漏。
- 统计置信度校准。

## 21. 第一阶段验收标准

第一阶段完成时应满足：

1. 可以通过一条命令创建新比赛文件。
2. 新比赛文件包含完整且可校验的 YAML 元数据。
3. 每场比赛拥有唯一 `match_id`。
4. 比赛文件明确区分赛前、临场、赛果和复盘章节。
5. 校验工具可以发现字段缺失、非法状态和无效图片引用。
6. 赛前最终结论可以被锁定并产生哈希。
7. Git 可以追踪赛前锁定和赛后复盘之间的变化。
8. 当前原始资料和旧脚本得到完整保留，不发生信息丢失。

## 22. AI 接入验收标准

AI 接入完成时应满足：

1. AI 不需要一次加载整个资料目录。
2. AI 可以检索相关知识和相似比赛。
3. 每个核心判断都能列出支持证据和反向证据。
4. AI 输出包含引用过的本地资料。
5. AI 明确列出缺失信息，不虚构盘口或伤停数据。
6. AI 无法读取当前比赛尚未到达阶段的章节。
7. 历史回测启用严格时间过滤并记录资料版本。
8. AI 可以选择 `pass`，而不是强制输出方向。
9. AI 生成内容不会未经审核直接升级为高可信知识规则。
