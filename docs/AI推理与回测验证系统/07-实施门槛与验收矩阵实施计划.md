# 实施门槛与验收矩阵实施计划

## 目标与审查结论

将原路线图转为可执行依赖图和发布门禁。审查后修正：4-6 周、30/60 场、成本阈值和 Schema/代码行数均为规划估计，不是系统硬编码事实；AI 优势必须按市场、独立比赛和不确定性报告，不能由 30 场总样本直接判定“系统性更优”。

## 实施顺序

1. **Phase 00 治理底座**：完成受信资产快照、默认拒绝出站、FakeProvider、证据校验、AI 台账和 Analytics 指纹。未通过前禁止真实 provider、pilot、Primary。
2. **Phase 01 数据资格**：完成 Dataset Manifest、fixture/case 去重、历史/反事实双入口和固定时间锚点。未通过前禁止任何回放或 AI 对比。
3. **Phase 02 确定性回放**：完成 prediction/label/outcome 隔离、代码化结算和基线报告。未通过时间泄漏、亚盘和历史兼容测试前禁止 AI primary。
4. **Phase 03 AI 运行底座**：实现 sandbox、配置激活、五阶段编译、sealed run 和 FakeProvider；真实 provider adapter 需独立安全批准。
5. **Phase 04 前瞻性影子运行**：实现 Study、Primary claim、赛后 Outcome、分层报告；先 pilot，再 confirmatory。
6. **Phase 05 人工提案**：在预先声明的 30 场以上独立市场样本达到探索门槛后，人工创建 intake 和新实验 revision。
7. **可选案例重排**：仅在预注册分析表明 BM25 失败率和案例缺失与结果存在可解释关联时实施；否则保持现有检索。

## 公共接口与数据迁移

- 新增约定的 Schema、CLI、台账和 Analytics 表必须按 Phase 00-05 分批注册；每批提高 Analytics schema version 并把所有新增权威文件纳入 `_fingerprint()`。
- 新命令统一从 `scripts/odds-journal.ps1` 调用；输出使用内容寻址目录和追加式台账，SQLite 只作可删重建投影。
- 不迁移或改写正式规则、已有 Match、历史回执、已锁定比赛、既有规则实验或正式统计。所有 AI/回放数据使用新目录和新表。
- 每一 Phase 均必须能单独禁用，且不会让下一 Phase 的 CLI、目录或台账被误用为正式轨输入。

## 验收门禁

1. 所有阶段：AI 开关、异常、配置变化前后，正式 Outlook、Lock、Settlement、Review 和正式统计哈希不变。
2. 回放前：资格、冲突、来源、去重、时间泄漏和标签隔离测试必须全部通过。
3. AI 前：sandbox 无真实数据/网络/权威写入；外部调用需白名单、lcz 批准、价格和预算，任一不符 fail closed。
4. confirmatory 前：Study 已注册、Primary 唯一、封存早于 kickoff、正式输入未 stale、结果不存在。
5. 报告：严格按市场、独立 fixture、sample relation 和 capability profile 分层；少于 30 个独立样本仅为探索性报告。成本上限和 5%/10% 差异作为 Study/人工决策中明确记录的可调整阈值，不写死为发布条件。
6. 规则发布：仍要求独立 cohort、既有 validation study 门禁、人工批准和独立 `rules release`；AI 实验激活绝不等于规则发布。

## 验证与交付

- 每个 Phase 完成时运行其目标单测，再运行 `schemas check`、`analytics build`、`analytics validate`、`evidence validate`、`case validate`、`validate --all` 和全量 pytest。
- 变更 CLI、Schema、manifest、可信 Prompt/策略或治理文件后执行 `agent changes`；出现 `workflow_breaking` 时，在工作区干净且测试通过后按既有机制运行 `agent sync`。
- 发布每个 Phase 前记录：实现 commit、Schema/Analytics 版本、完整测试结果、已知限制、未激活的后续能力和回退方式。

## 规划假设

- 开发周数、测试数量、Schema/表数量和每周赛事数量只用于排期；实现以验收门禁而非工期推算为准。
- 真实 provider、外部费用和具体模型选择需在对应配置激活前由 lcz 明确批准。
